# Thor.DataLayer

Shared EF Core data-access package for Thor. It owns:

- **Data models** — EF Core entities live under `Models/` and are mapped via
  `TenantDbContext` (per-tenant DB) or `MasterDbContext` (Master metadata DB).
- **Migrations** — schema changes are managed with EF Core migrations
  (`Migrations/`, generated by the `dotnet ef` CLI).
- **Repositories** — generic CRUD access (`Repositories/IRepository.cs`,
  `Repositories/Repository.cs`) that entity-specific repositories build on.
- **Tenant database connections** — `Data/TenantDbContextFactory.cs` wraps an
  already-open, tenant-validated connection in a `TenantDbContext`.

## What this package deliberately does *not* do

Thor is database-per-tenant on a shared Aurora PostgreSQL cluster (see
`docs/architecture/ADR.md` §6). This package is **tenant-agnostic**: it does
not resolve *which* tenant to connect to. Callers are responsible for
resolving the tenant's routing and opening the connection (authenticated with
an RDS IAM token — there is no password auth path; see
`Thor.DataConnectionManager`) and passing that connection in. This keeps the
boundary clean — tenant resolution/routing logic belongs to the caller, not to
the data layer.

```csharp
using var db = await tenantConnectionManager.GetTenantDbContextAsync(tenantId, cancellationToken);
```

## Consuming this package

This is a **project**, consumed via `<ProjectReference>` — not packaged or
published anywhere. Every consumer lives in this same repo (`Thor.Api`,
`Thor.TaskApi`, `Thor.DataConnectionManager`, etc.), so there's no packaging
step: build the consuming project and you get the current source directly.

```xml
<ItemGroup>
  <ProjectReference Include="..\..\shared\Thor.DataLayer\Thor.DataLayer.csproj" />
</ItemGroup>
```

(adjust the relative path to wherever the consuming project sits under `backend/`).

## Adding a model and generating a migration

1. Add the entity class under `Models/`.
2. Add a `DbSet<TEntity>` property to `Data/TenantDbContext.cs` (per-tenant DB)
   or `Data/MasterDbContext.cs` (Master metadata DB).
3. Generate a migration using the matching design-time factory
   (`Data/TenantDbContextDesignTimeFactory.cs` or
   `Data/MasterDbContextDesignTimeFactory.cs`), which needs no real, reachable
   Postgres server — `migrations add` builds the model in memory and never
   opens the connection. Both design-time factories fall back to
   `localhost:5432` with a `postgres`/`postgres` login if
   `THOR_DATALAYER_*`/`THOR_MASTERDB_*` env vars are unset — convenient for
   local dev, but only for `migrations add` (schema diffing), not for
   `database update` against a real database.

   **Master DB:** commit the generated migration as usual. This is a
   deliberate exception to the "don't commit generated code" policy — Master
   is one long-lived, already-populated database per environment, migrated
   in place by `Thor.DbBootstrap.Function`, so it needs real incremental
   migration history the way Tenant DB doesn't (see
   `scripts/publish-lambda-functions.sh` for the full reasoning):

   ```sh
   dotnet ef migrations add <MigrationName> --project backend/shared/Thor.DataLayer --context MasterDbContext --output-dir Migrations/Master
   ```

   **Tenant DB:** do **not** commit a migration — `Migrations/Tenant/` is
   git-ignored (org policy prohibits committing generated/tool-output code).
   `scripts/publish-lambda-functions.sh` regenerates a single
   `InitialTenantSchema` migration from the current model immediately before
   every Lambda publish, so the tenant schema is always built fresh from
   `TenantDbContext.cs`, never from a stored migration history. To inspect
   the generated migration locally, run the same command yourself (adjust
   `<MigrationName>` freely — it's discarded either way) and don't stage it:

   ```sh
   dotnet ef migrations add <MigrationName> --project backend/shared/Thor.DataLayer --context TenantDbContext --output-dir Migrations/Tenant
   ```

   Because this project has two `DbContext` types, `--context` is required
   on every `dotnet ef` invocation — omitting it is ambiguous.

   If the env vars are unset, both design-time factories fall back to
   `localhost:5432` with a `postgres`/`postgres` login — convenient for local
   dev, but only for `migrations add` (schema diffing), not for `database
   update` against a real database.

For Master DB schema changes: add the EF Core migration, commit it, done —
there's no version bump or repack step. Tenant DB schema has no committed
migration history to apply incrementally, so rolling a schema change out
across the tenant fleet always goes through the Blue/Green deployment
strategy described in `docs/architecture/ADR.md` §6.4 — there is no in-place
"apply the diff to an existing tenant DB" path.


For schema changes specifically: add the EF Core migration, done — there's no
version bump or repack step anymore. Rolling a new Master DB schema out is a
normal migration; rolling tenant DB schema changes out across the tenant
fleet follows the Blue/Green deployment strategy described in
`docs/architecture/ADR.md` §6.4.

## Seed scripts

`Scripts/LocalSeed/` has SQL scripts for populating local/dev data, one per flow. These
are for a local Postgres instance only — they are never run against a deployed
(dev/staging/prod) database.

- **Connector types** — `00_connector_types.sql` (Master DB) — `connector_types`, the
  canonical id->name lookup that `authentication_types`/`connector_config_fields` (real
  FK, same database) and every tenant-DB ingestion table (application-level reference
  only, no physical FK) key off of. Run first.
- **Authentication method** — two scripts, since Master and Tenant are separate
  databases with no physical FK between them. Run in order:
  1. `01_authentication_method_master.sql` (Master DB) — `authentication_types` and
     their `authentication_fields` (the fields each type requires, e.g.
     username/password). Depends on `00_connector_types.sql`.
  2. `02_authentication_method_tenant.sql` (Tenant DB) — `authentication_methods`,
     whose `type` column is a cross-database reference to the ids inserted in step 1.
- **Source** — `03_source.sql` (Tenant DB) — `source`.
- **Connector config fields** — `04_connector_config_fields.sql` (Master DB) —
  `connector_config_fields`, the non-authentication per-connector settings (e.g. a search
  base or page size) a tenant's ScanConfig supplies a value for. Depends on
  `00_connector_types.sql`.
- **Tenant** — `05_tenant.sql` (Master DB, schema `auth`) — `tenant` and `tenant_routing`,
  the identity + routing metadata `TenantRoutingResolver` resolves at request time to open
  a connection to the tenant's own database. No dependency on the other scripts here.

All six use fixed ids and `ON CONFLICT ... DO NOTHING`, so they're safe to re-run. Edit
the placeholder `VALUES` rows in each file before running.

Run them with `psql` against a local Postgres instance. If you don't have `psql`
installed but have the repo's local dev Postgres running in Docker (e.g. a
`thor-postgres` container), run it through the container instead. PowerShell has no
`<` input-redirection operator (unlike Bash), so pipe the file content in with
`Get-Content` rather than redirecting:

```powershell
# Master DB (run in order — 01 depends on ids inserted by 00 above)
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\00_connector_types.sql |
  docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE>
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\01_authentication_method_master.sql |
  docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE>
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\04_connector_config_fields.sql |
  docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE>
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\05_tenant.sql |
  docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE>

# Tenant DB (run in order — 02 depends on ids inserted by the Master script above)
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\02_authentication_method_tenant.sql |
  docker exec -i thor-postgres psql -U <THOR_DATALAYER_USER> -d <THOR_DATALAYER_DATABASE>
Get-Content backend\shared\Thor.DataLayer\Scripts\LocalSeed\03_source.sql |
  docker exec -i thor-postgres psql -U <THOR_DATALAYER_USER> -d <THOR_DATALAYER_DATABASE>
```

In Bash (e.g. Git Bash), `<` redirection works as usual:

```sh
docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE> \
  < backend/shared/Thor.DataLayer/Scripts/LocalSeed/00_connector_types.sql
docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE> \
  < backend/shared/Thor.DataLayer/Scripts/LocalSeed/01_authentication_method_master.sql
docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE> \
  < backend/shared/Thor.DataLayer/Scripts/LocalSeed/04_connector_config_fields.sql
docker exec -i thor-postgres psql -U <THOR_MASTERDB_USER> -d <THOR_MASTERDB_DATABASE> \
  < backend/shared/Thor.DataLayer/Scripts/LocalSeed/05_tenant.sql
```

Substitute `-U`/`-d` with the `THOR_MASTERDB_*`/`THOR_DATALAYER_*` values from your
`.env` (see `.env.example`). With a local `psql` client installed instead, drop the
`docker exec -i thor-postgres` prefix and add `-h localhost -p 5432`.

# Thor Backend APIs

API interface for handling all authenticated incoming traffic from clients.

Sibling services it talks to: [Thor.TaskAPI](../Thor.TaskAPI/README.md) (proxied under
`/task-api/*`) and [Thor.IntelligenceEngine](../Thor.IntelligenceEngine/README.md) (over gRPC).

## API Versioning

Versioning is handled by `Asp.Versioning.Mvc`, configured in `Program.cs`.

- **Scheme:** URL segment (`/v{version}/...`), e.g. `/v1/authentication-methods`.
- **Default version:** `1.0` — assumed when no version segment is present.
- **Supported versions:** `1.0` (`Controllers/V1`).

### Response headers

- `api-version` — the version that actually served the request (e.g. `1.0`).
- `api-supported-versions` / `api-deprecated-versions` — emitted automatically
  (`ReportApiVersions = true`) listing all versions the matched endpoint supports/deprecates.

### Adding a new version

1. Add a `Controllers/V{n}` folder with a controller decorated with `[ApiVersion("{n}.0")]`
   and `[Route("v{version:apiVersion}/...")]`.
2. Deprecate old versions via `[ApiVersion("1.0", Deprecated = true)]` rather than removing them.

## Configuration

Every value below is required — `RequiredEnvironment.GetVariable` throws at startup rather than
falling back to a dev default (ADR §5/§6). Locally they come from `.env` (loaded by `DotNetEnv` in
`Program.cs`); see `.env.example`. In deployed environments Terraform injects them, and **nothing
is set by hand on a task definition** — see `infra/src/main.tf` (`service_app_environment` /
`service_app_secrets`).

| Variable | Deployed source |
|----------|-----------------|
| `THOR_MASTERDB_HOST` / `_DATABASE` / `_USER` / `_REGION` / `_PORT` | `local.masterdb_environment` — host is the RDS Proxy endpoint, auth is RDS IAM (no password) |
| `THOR_TASKAPI_JWT_PRIVATE_KEY` | ECS `secrets` → `thor-<env>-secret-connector-jwt`, `private_key` field |
| `THOR_API_KEY_PEPPER` | ECS `secrets` → `thor-<env>-secret-api-key-pepper` |
| `THOR_INTELLIGENCE_ENGINE_GRPC_ADDRESS` | Service Connect alias, `https://intelligence-engine:8443` |
| `ReverseProxy__Clusters__task-api-cluster__Destinations__primary__Address` | Service Connect alias, `https://task-api:8443/` — overrides the local-dev destination in `appsettings.json`, which resolves to nothing in a container |
| `ReverseProxy__Clusters__task-api-cluster__HttpClient__DangerousAcceptAnyServerCertificate` | `true` — task-api serves a self-signed cert (`CN=task-api.internal`) baked in by its Dockerfile |
| `TLS_CERT_PFX_PATH` / `_PASSWORD` | `infra/src/modules/ecs/services.tf`; the cert itself is baked into the image by the Dockerfile |
| `THOR_TENANT_ASSETS_BUCKET` | `module.frontend` output — the tenant-assets bucket the frontend CloudFront serves under `/tenant-assets/*` (tenant login-page logos) |

This is the **only** service holding the connector JWT private key — it alone mints connector
tokens; Thor.TaskApi and the authorizer only verify them (ADR §5.2).

> `.env.example` ships a working dev keypair and pepper. They are committed, so treat any
> environment using them as having no connector-token security at all. Deployed environments get
> their own, generated by `scripts/seed-connector-secrets.sh` — never copy these values forward.

### How a missing value fails

Worth knowing because the failure modes look nothing alike:

- `THOR_TASKAPI_JWT_PRIVATE_KEY` and `THOR_API_KEY_PEPPER` are read eagerly into
  `ConnectorSecurityOptions`, so the host dies at startup with
  `Required environment variable '...' is not set` and the task crash-loops. Both are arguments to
  the same constructor — setting only one just moves the fatal to the next argument.
- `THOR_INTELLIGENCE_ENGINE_GRPC_ADDRESS` is read inside an options delegate, so the service starts
  cleanly and passes `/health`; the first Intelligence Engine call fails instead.
- The `ReverseProxy__*` overrides never fail startup at all. Without them `/task-api/*` proxies to
  `localhost:5081` inside this container and every proxied call errors.

The connector JWT keypair and the API-key pepper are seeded out-of-band — see
`infra/bootstrap/connector-secrets.md`.

## Deployment

Built and deployed by `.github/workflows/deploy.yml`, which triggers on changes under
`backend/services/Thor.API/**`, `backend/shared/**`, or `proto/**`.

- Push to `dev` — builds from source and deploys, then records the image digest in
  `deploy/thor-api/image.json`.
- Push to `qa` / `main` — promotes the digest already in that manifest; no rebuild.
- Manual deploy/rollback — run the `Deploy` workflow with `service: thor-api` and,
  optionally, an explicit `image_digest`.

### A config change needs a deploy, not just an apply

The ECS service sets `lifecycle { ignore_changes = [task_definition, ...] }`, because CI owns which
revision is live. A Terraform apply that changes this service's configuration therefore **registers
a new task definition revision and stops** — the running service stays on the revision it was
already on, with the old configuration, and nothing restarts.

The deploy workflow is what moves it: it reads the family's latest ACTIVE revision (the one the
apply registered), patches only the image, and updates the service. Three consequences:

- **Apply before deploying.** A deploy that runs first carries the *old* revision's configuration
  forward and skips straight past the apply's revision.
- **Seed secrets before deploying.** ECS resolves `secrets` at task start. A secret that exists but
  has no value yet fails that call and the task never starts — `ResourceInitializationError`,
  before any application log line.
- **Re-seeding is not live.** `scripts/seed-connector-secrets.sh` writes a new keypair and pepper,
  but a running task keeps whatever it resolved at start, so nothing changes until this service is
  redeployed. The script also drops the public half in
  `infra/envs/<env>/connector-jwt-public-key.pem`, which this service never reads — that file is
  the authorizer's copy, a literal Lambda env var, and only moves on a commit plus apply. Seed,
  commit the `.pem`, apply, then deploy; thor-api, task-api and the authorizer must all end up on
  the same keypair or connector tokens stop verifying somewhere.

Rolling all three onto a freshly seeded keypair is the `Roll services` workflow
(`.github/workflows/roll-services.yml`, run manually against one environment). It forces a new
deployment on thor-api, task-api and intelligence-engine without changing their images — the secrets
arrive as `valueFrom` ARNs, so ECS re-resolves them when the new tasks start.

An ordinary deploy no longer does this. It used to: every `ecs-deploy` also redeployed the two
siblings on their current image, which tripled the blast radius of every deploy to solve a problem
that only exists just after a manual rotation, and resolved each sibling's image from the family's
latest *registered* revision — which a `terragrunt apply` may have just pinned to `<repo>:latest`.
